# IC 驱动开发规范

## 正文

### 1. 文档定位

这份文档是单器件驱动实现补充规范。

它依附于 `docs/嵌软开发规范.md` 存在。
项目级边界、目录分层、工具链、生成代码边界、AI 自动加载入口和文档维护规则，未特别说明时都以项目规范为准。

本文件重点管 `device`、`platform`、`app` 三层在器件接入时怎么分工，怎么落地，怎么验证。

相关文档入口如下。

- 项目级主规范位于 `docs/嵌软开发规范.md`。
- 仓库级自动加载规则位于 `.github/copilot-instructions.md` 与 `.github/instructions/*.instructions.md`。

### 2. 核心理念与目标

本规范的目标，是让 IC 驱动代码具备高可移植性、高稳定性和可维护性。

底层驱动设计方法，主要参考 ST Standard C Drivers 的平台无关模式。  
做法是通过 `ctx` 注入 `read`、`write`、`delay` 等接口，把器件寄存器逻辑和具体 MCU、HAL 分开。

这份规范来自多个传感器在接入、联调、异常定位和重构中的共性经验。  
它优先保留跨器件、可复用、能落地的规则，不追求覆盖所有特殊项目形态。

- 器件驱动可移植性优先。器件驱动核心逻辑必须和硬件平台解耦，确保无需修改即可移植到不同 MCU。
- 运行期鲁棒性优先。系统必须具备自动检测故障并从错误中恢复的能力，例如传感器掉线、数据异常等场景。
- 分层要清楚。业务逻辑、驱动逻辑、硬件适配层必须分开。

### 2.1 器件接入卡

开始接新器件、重写驱动或大改寄存器配置前，先确认这些事实。

- 器件型号、料号后缀和所用数据手册版本。
- 总线类型，以及地址或片选。
- 复位脚、电源控制脚、中断脚。
- boot wait、ID 寄存器、复位完成判据。
- 校准系数、OTP 或补偿参数的来源与读取方式。
- 超时、重试和恢复路径。
- 是否存在共享总线、RTOS、低功耗或 FIFO。
- 首包发布门控和最小诊断输出方式。

若其中某项还不明确，先查手册、现有代码和仓库文档，再进入代码生成。

### 3. 架构分层原则

#### 3.1 分层职责

| 层级 | 模块位置 | 职责描述 | 允许的依赖 |
| :--- | :--- | :--- | :--- |
| **应用层 (App)** | `app/`, `main.c` | 业务调度、数据处理、故障监测与恢复、调试输出（VOFA、Printf） | Device, Middleware, Platform, HAL |
| **器件驱动层 (Device)** | `device/` | **器件驱动核心逻辑**。处理寄存器协议、状态机、数据转换。 | **仅依赖标准 C 库和 ctx 注入的接口** |
| **中间件层 (Middleware)** | `middleware/` | 协议、算法、存储、日志等可复用能力模块。 | 标准 C 库, Device |
| **平台适配层 (Platform)** | `platform/` | **硬件抽象**。实现具体的 I2C、SPI 读写和延时函数。 | HAL, BSP |

#### 3.2 边界要求

- Device 层要保持干净。严禁包含 `main.h`、`stm32_hal.h` 等硬件相关头文件。严禁直接调用 `HAL_` 开头函数。
- Middleware 层只做能力复用。协议、算法、日志、存储等通用模块，不应承载具体器件寄存器协议。
- Platform 层可以处理具体芯片细节，例如 DMA、中断、模拟时序。
- App 层负责兜底。它要处理 Device 或 Middleware 返回的错误，并执行重试或重启策略。

### 4. 强制性规范（MUST）

#### 4.1 可移植性规范

1. **上下文注入**：驱动必须通过结构体指针 `ctx` 传入读写函数、延时函数和句柄。禁止在驱动内部定义全局硬件句柄。
2. **环境隔离**：Device 代码中不得出现特定平台的宏定义，例如 `#ifdef STM32F1`。所有平台差异必须通过适配层屏蔽。
3. **HAL 依赖隔离**：Device 层严禁直接调用 HAL 函数，例如 `HAL_Delay`。必须通过 ctx 注入的函数指针实现。
4. **生成代码边界隔离**：使用 CubeMX 或其他代码生成工具时，所有用户自定义 include、变量、函数声明和业务逻辑，必须放入 USER CODE、自定义扩展区或独立用户文件中。禁止写入会被生成器覆盖的区域。
5. **上下文字段不得形同虚设**：Platform 层若定义了 `ctx.handle` 或 `ctx.priv_data`，则必须按设计真实消费。禁止一边保留上下文字段，一边在实现中硬编码全局总线句柄、固定片选或固定实例，导致 ctx 只剩形式上的注入。

#### 4.2 鲁棒性与容错规范

1. **参数强校验**：所有对外接口 API 必须检查指针是否为空，枚举值是否在合法范围内。
2. **超时机制**：所有涉及硬件等待的循环，例如 `WaitUntil`、`While`，都必须包含超时退出机制。超时时间必须使用宏定义。
3. **通信失败必须有限退出并具备恢复策略**：Platform 层通信函数，例如 SPI、I2C 读写，必须保证失败可返回，禁止无限阻塞。默认建议采用有限次重试。若总线存在卡死风险，还应在重试前后加入必要的总线恢复或事务清理步骤。对于实时敏感场景，允许由 App 层接管是否重试与重试次数。
4. **传感器 ID 验证**：初始化时必须读取并验证传感器 ID，确保连接正确的传感器。
5. **初始化时序必须完整**：参考 ST 标准示例，初始化流程至少应覆盖 `platform_init -> boot wait -> device id check -> software reset -> reset complete poll -> key configuration`。其中软件复位后必须轮询确认复位完成，禁止写完复位位后立即继续后续配置。
6. **关键配置回读校验**：初始化中凡是写入工作模式、数据速率、量程、复位位等关键控制寄存器后，必须回读确认配置已真实生效。校验失败必须返回错误，不得静默继续运行。
7. **最小诊断通道保留**：外设初始化失败、配置失败或数据异常时，系统必须保留最小可观测通道。日志、串口、心跳、状态字至少保留一种，避免进入无输出、无状态的不可诊断状态。
8. **校准区、OTP、系数读取失败不得静默吞错**：初始化阶段凡是读取校准系数、补偿参数、OTP 或器件内部配置镜像时，一旦底层通信失败，必须显式返回错误。禁止以 `0`、默认值或半有效数据代替失败结果继续初始化。
9. **冷启动和复位瞬态治理**：对于连续物理量传感器，若冷启动、软复位或重初始化后的前几帧数据可能污染上位机显示、控制闭环或日志判断，App 层必须具备预热加稳定发布门控，或等价机制。允许内部滤波先收敛，但在稳定条件满足前不得对外发布。
10. **调试回传时间基准统一**：联调期用于波形和日志分析的回传数据，必须包含时间基准，例如 `tick` 或单调递增序号，用于区分真实物理跳变和系统复位、回绕、重启。
11. **数据异常监测**：应用层必须检查数据合理性，例如是否全为 0、是否超出物理量程、是否明显跳变。典型范围示例：温度 `-50°C ~ 100°C`、压力 `>0 且 <=200000 Pa`、湿度 `0% ~ 100%`。

#### 4.3 编码与寄存器操作规范

1. **宏化管理**：所有寄存器地址、位掩码、配置字、命令字、超时时间、重试次数必须使用宏或枚举定义。禁止在流程代码中散落魔数 `Magic Number`。
2. **宏的分层归属必须正确**：
   - 器件寄存器地址、位定义、默认配置值、命令字属于 Device 层。
   - 总线实例、片选引脚、DMA 通道、平台超时、平台重试次数属于 Platform 层。
   - 物理量换算阈值、业务告警阈值、滤波参数、QNH 等业务参数属于 App 或 Middleware 层。
3. **寄存器修改必须避免误伤其他位**：修改控制寄存器时，必须保证未涉及的位保持不变。优先采用读字节、掩码修改、写回模式。
4. **总线协议附加位必须由 Platform 层处理**：若器件 SPI、I2C、I3C 通信协议要求在读写函数中附加读位、写位、多字节自增位或其他协议控制位，必须在 Platform 层统一处理，不能泄漏到 Device 或 App 层。
5. **模块内部辅助函数应默认使用内部链接**：仅在模块内部使用的计算、解析、状态判断函数，应优先声明为 `static`，避免无意暴露为跨文件符号。
6. **多字节原始数据拼装必须显式处理字节序与符号扩展**：Device 层在解析 16、24、32 位寄存器原始数据时，必须使用位移与掩码显式拼装。禁止把总线缓冲区直接强转为多字节整型指针。

### 5. 实现模板参考

#### 5.1 驱动上下文定义（Device）

```c
// device/xxx_driver.h
typedef struct {
    int32_t (*write_reg)(void *handle, uint8_t reg, const uint8_t *data, uint16_t len);
    int32_t (*read_reg)(void *handle, uint8_t reg, uint8_t *data, uint16_t len);
    void (*delay_ms)(uint32_t ms);
    void (*lock)(void *handle);
    void (*unlock)(void *handle);
    void *handle;
    void *priv_data;
} xxx_ctx_t;
```

补充约束如下。

1. `ctx` 只描述驱动所需能力，不暴露具体 HAL 名称。
2. `handle` 只做平台对象透传，例如 SPI 句柄、I2C 句柄或组合句柄。
3. `priv_data` 为可选项，用于额外平台上下文。项目暂不需要时可以不启用。
4. `lock`、`unlock` 主要用于 RTOS、多任务或共享总线场景。裸机单循环工程可不启用。
5. Device 层对 `ctx` 的使用必须是无状态或最小状态。禁止把平台资源缓存为模块级全局变量。
6. 多总线实例或多个同型器件必须依赖 `ctx` 区分。禁止靠文件内静态全局句柄切换目标设备。

#### 5.2 寄存器建模与访问模式

##### 5.2.1 读改写是默认模式

对控制寄存器的常规修改，默认应采用以下模式。

```c
uint8_t reg_val;

ret = xxx_read_reg(ctx, XXX_CTRL_REG, &reg_val, 1);
if (ret != 0) {
    return ret;
}

reg_val &= (uint8_t)(~XXX_CTRL_ODR_Msk);
reg_val |= ((uint8_t)odr << XXX_CTRL_ODR_Pos);

ret = xxx_write_reg(ctx, XXX_CTRL_REG, &reg_val, 1);
return ret;
```

约束如下。

1. 先读后改，避免覆盖保留位和其他功能位。
2. 掩码和位移必须由宏统一定义，不能直接写裸常数。
3. 写回后如该寄存器属于关键控制项，应继续执行回读校验。
4. 多字节连续读写位等总线协议细节，由 Platform 读写函数处理。

##### 5.2.2 跨寄存器字段必须显式拆分与重组

若一个逻辑配置项分散在多个寄存器中，驱动层必须提供统一封装接口。  
由驱动内部负责拆分与重组，不能把拼装细节泄漏给 App 层。

```c
uint8_t combined_val;

combined_val = ((reg_high_field << 4) | reg_low_field);
```

要求如下。

1. `set` 接口内部完成位拆分并分别写入多个寄存器。
2. `get` 接口内部完成多个寄存器字段读取与重组。
3. App 层只面对语义化枚举值，不直接操作碎片化位段。
4. 对多字节原始数据，必须通过移位和掩码显式处理字节顺序与符号扩展。

##### 5.2.3 位域映射的使用边界

1. 位域主要用于提升寄存器语义可读性，不应替代全部寄存器访问策略。
2. 涉及跨编译器、跨架构、对齐不确定性的项目，优先使用掩码宏。
3. 若采用位域，必须明确大小端处理方式，并确认结构体大小与目标寄存器宽度严格一致。

#### 5.3 容错恢复逻辑（App）

```c
// app/xxx_app.c
void XXX_Loop(void) {
    int ret = xxx_read_data(&ctx, &data);

    if (ret != 0) {
        error_count++;
    } else if (data.temperature < -50.0f || data.temperature > 100.0f ||
               data.pressure <= 0 || data.pressure > 200000) {
        error_count++;
    } else {
        error_count = 0;
    }

    if (error_count > MAX_ERROR_THRESHOLD) {
        xxx_reset(&ctx);
        xxx_init(&ctx);
        error_count = 0;
    }
}
```

#### 5.4 初始化最小流程

建议顺序如下。

1. 基础平台初始化成功。
2. 最小诊断通道可用。
3. 完成 boot wait。
4. 器件 ID 校验通过。
5. 必要时执行软件复位，并轮询确认复位结束。
6. 写入关键寄存器并回读确认。
7. 校准系数、OTP 或关键补偿参数读取成功。
8. 进入业务循环前，至少完成一次系统状态、器件状态、业务数据的联调验证。

#### 5.5 Platform 层事务重试模板

```c
#define XXX_BUS_TIMEOUT_MS   10U
#define XXX_BUS_RETRY_COUNT  3U

static int32_t XXX_ReadReg(void *handle, uint8_t reg, uint8_t *data, uint16_t len)
{
    uint32_t retry;

    for (retry = 0; retry < XXX_BUS_RETRY_COUNT; retry++) {
        XXX_Select(handle);

        if (Bus_SendCmd(handle, reg) != 0) {
            XXX_Deselect(handle);
            continue;
        }

        if (Bus_ReadData(handle, data, len) != 0) {
            XXX_Deselect(handle);
            continue;
        }

        XXX_Deselect(handle);
        return XXX_ERR_NONE;
    }

    return XXX_ERR_COMM;
}
```

约束如下。

1. 重试次数必须有限且宏化，禁止无限重试。
2. 每次失败后都必须完整收尾，例如释放 CS、清状态位、恢复总线空闲态。
3. 默认重试应发生在 Platform 层。若项目对实时性极敏感，可由 App 层基于返回码决定是否继续重试。
4. 若总线事务存在时序要求，重试前必须补足必要延时或恢复序列。

#### 5.6 生成文件边界规范

1. 业务 include、模块头文件、静态变量、函数原型放入 USER CODE 对应区域。
2. 复杂业务逻辑尽量放入 `app/`、`device/`、`platform/` 等独立文件。生成文件仅保留调用入口。
3. 不要把关键初始化、通信流程、状态机主体直接写在生成器可覆盖区。
4. 每次重新生成后，至少检查 include 区、私有变量区、函数声明区和主循环调用点是否仍完整。

### 6. 推荐性规范与联调建议（SHOULD）

1. **非阻塞延时**：在应用层轮询 `Loop` 中，建议使用基于时间戳 `Tick` 的非阻塞调度，避免使用 `HAL_Delay` 阻塞 CPU。
2. **调试分离**：调试代码，例如 VOFA+ 波形发送、Printf 日志，应置于 `main.c` 或独立调试模块中。严禁混入 `device` 驱动文件。
3. **错误码统一**：建议定义错误码枚举统一错误表示，例如：
   ```c
   typedef enum {
       XXX_ERR_NONE = 0,
       XXX_ERR_PARAM = -1,    // 参数错误
       XXX_ERR_COMM = -2,     // 通信错误
       XXX_ERR_TIMEOUT = -3,  // 超时
       XXX_ERR_CONFIG = -4,   // 配置错误
       XXX_ERR_ID = -5,       // ID 不匹配
   } XXX_Error_t;
   ```
4. **寄存器操作优先采用掩码字节读改写**：对于控制寄存器，优先采用读字节、掩码修改、写字节的方式，避免依赖位域布局造成跨编译器、跨平台差异。
5. **位域仅作受控场景下的表达工具**：若必须使用位域结构体映射寄存器，必须满足以下条件：
   - 仅映射单字节寄存器，不跨字节拼接位域。
   - 明确字节序条件编译，避免不同编译器布局差异。
   - 不将位域结构体作为通用线协议序列化格式。
   - 对可移植性要求高的项目，仍应优先选择掩码宏而非位域。
6. **正式协议如资源允许也建议保留时间基准**：即便脱离联调阶段，在波形、日志或二进制流中仍建议保留 `tick`、序号或帧计数，以便后续定位发送异常和业务数据未刷新。
7. **对外读取接口应尽量无副作用**：类似 `get`、`read_cached`、`channel_get` 的接口，建议只返回当前状态或缓存值，不顺带推进状态机、清错误计数或触发总线访问。若接口确有副作用，应在命名和注释中明确说明。
8. **共享总线项目建议显式提供并发保护方案**：若项目运行在 RTOS、多任务或中断、线程共享总线环境中，建议在 Platform 层提供互斥、锁或总线仲裁方案，避免多个调用者并发访问同一总线或同一器件。
9. **存在低功耗或待机场景的器件应补充电源状态恢复设计**：若器件支持 standby、sleep、forced mode、掉电后寄存器丢失或通道级功耗切换，建议明确 suspend、resume 后哪些寄存器需要重写、哪些校准数据需要重读，以及恢复后的首包数据是否需要再次门控。
10. **建议显式区分采样触发接口与缓存读取接口**：对连续采样、后台更新或带 FIFO、批量读取能力的器件，建议把触发采样、刷新缓存、读取缓存、对外发布分成不同接口或阶段，避免上层误把 `get` 当作隐式采样入口。
11. **建议为关键配置建立最小验证矩阵**：当器件存在多个 ODR、量程、滤波档位、工作模式或中断、FIFO 组合时，建议至少维护一份默认配置、边界配置、异常恢复后配置的最小验证矩阵，避免驱动只在单一默认参数下可用。

#### 6.1 新建器件接入阶段的人侧协作约束

- 如果准备让 AI 参与新器件接入，先由人尽量搜索并确认关键事实，包括总线类型、目标 MCU、是否裸机或 RTOS、是否允许阻塞、是否有低功耗、是否需要中断或 FIFO、是否存在共享总线。
- 对寄存器地址、位定义、复位值、启动等待时间、校准系数格式、端序、FIFO 语义等事实，优先查数据手册、现有驱动、仓库文档或已验证参考实现。不要把猜测过的事实当成明确输入交给 AI。
- 给 AI 下任务时，应把器件边界条件、实现落层、最小验证步骤、不可猜测项一起说明，不要只给功能目标。
- 对新器件接入，优先让 AI 先给出 `device/platform/app` 拆分方案、初始化顺序、错误恢复策略和最小验证步骤。确认后再逐段生成代码。
- 若 AI 产出了寄存器配置或初始化序列，人应继续核对其是否与手册、已有代码和现有工程约束一致。未被确认的条目应退回待确认状态。

#### 6.2 分级回传测试

这一节用于联调期快速确认系统状态和回传是否正常。  
目标是快速定位问题，不追求复杂协议实现。

1. **按三组信息顺序测试**：
   - 系统、MCU 运行状态
   - 传感器、模块初始化状态
   - 业务采样数据
2. **按项目现有方式逐级降级验证**：遵循从顶层到底层、从复杂到简单的原则逐级回传。层数不固定，以能快速定位问题为准。
3. **失败继续**：上一层协议失败，不阻塞下一层协议验证。
4. **先验证、后常态化**：三组验证完成后，再切回常用协议进入正式循环。
5. **保持轻量**：简单测试只要求能看见状态变化与回传是否正常，不要求一次性引入复杂校验和大量字段。
6. **联调探测代码必须可收口**：模式扫描、临时测试帧、分级探测分支、VOFA 回传、屏幕显示等测试接口只能服务联调定位。定位完成后应回归单一稳定路径，避免测试代码长期影响默认主流程。
7. **测试接口优先保留但默认关闭**：对后续复测仍有价值的联调接口，进入正式工程后优先采用注释保留、条件编译开关或集中测试入口的方式保留，而不是直接删除。但必须确保默认关闭，不对正式业务路径形成隐式依赖。

注：如项目已有明确协议栈，可按项目约定将复杂到简单映射到具体协议。若接收到异常数据，也应保留最小回传能力，避免再次进入不可诊断状态。

#### 6.3 最小验证矩阵

| 场景 | 最少检查项 | 通过标准 |
| :--- | :--- | :--- |
| 默认配置 | ID 校验、关键寄存器回读、首包数据 | 初始化成功，关键配置真实生效，能够稳定出数 |
| 边界配置 | ODR、量程、模式边界 | 写入后回读一致，解析结果不越界 |
| 异常恢复 | 超时退出、重试、重初始化 | 失败能有限返回，恢复后能重新出数 |
| 冷启动或复位后 | 发布门控、时间基准、最小诊断输出 | 稳定前不对外发布，能区分瞬态与真实跳变 |

若器件支持低功耗、待机或 FIFO，还应在这四项之外补充对应的 suspend、resume 或批量读取验证。

### 7. 评审自检清单

提交前，先判断本次改动属于哪一类，再对照对应清单自查。不必每次从头扫完整张总表。

#### 7.1 新器件接入

- [ ] `ctx` 结构体完整，读写、延时和句柄注入齐全。
- [ ] `ctx.handle`、`ctx.priv_data` 被 Platform 实现真实消费，没有形式注入和硬编码并存的问题。
- [ ] 初始化流程覆盖 boot wait、ID 校验、软件复位、复位完成轮询和关键配置回读。
- [ ] 校准区、OTP、补偿参数读取失败时显式报错，没有以 `0` 或默认值继续运行。
- [ ] 默认配置已完成最小验证矩阵中的默认配置项。
- [ ] 异常恢复路径明确，通信失败后能够有限退出并重新出数。
- [ ] 冷启动或复位后的首包发布门控明确。
- [ ] 关键事实已从手册、现有代码或参考资料中确认来源。

#### 7.2 寄存器配置与数据解析改动

- [ ] `set_xxx` 或等价接口完成参数范围校验。
- [ ] 寄存器地址、位掩码、命令字和默认配置值仍放在 Device 层。
- [ ] 控制寄存器修改采用读改写或等价保护方式，没有误伤其他位。
- [ ] 多寄存器字段仍由 Device 层统一封装，没有泄漏到 App 层。
- [ ] 多字节原始数据通过移位和掩码显式拼装，没有直接强转缓冲区。
- [ ] 位域映射若继续使用，字节序、结构体宽度和适用边界仍然明确。
- [ ] `get`、`read` 类接口没有新增隐式副作用；若有，命名和注释已明确。

#### 7.3 Platform 总线适配改动

- [ ] Platform 层通信函数具备超时保护和有限次重试。
- [ ] 每次失败后都能完整收尾，不会把总线留在脏状态。
- [ ] SPI、I2C、I3C 的协议附加位仍统一封装在 Platform 读写函数中。
- [ ] 若存在共享总线、RTOS 或中断并发，互斥或仲裁方案已明确。
- [ ] 生成文件边界仍正确，自定义 include、变量和调用入口仍位于 USER CODE 或独立用户文件中。
- [ ] `device` 中没有回流 HAL 调用，也没有残留 `printf` 或串口发送调试代码。

#### 7.4 App 发布与恢复逻辑改动

- [ ] 应用层对全 0、越界、乱码或明显跳变的数据仍有合理性检查。
- [ ] 初始化失败或运行期异常后，App 层的限频重试、状态上报或降级运行路径仍成立。
- [ ] 冷启动、软复位、重初始化后的预热和稳定发布门控仍成立。
- [ ] 联调回传保留 `tick`、序号或等价时间基准。
- [ ] 分级回传、VOFA、显示等联调接口已收口管理，默认关闭，不形成正式路径依赖。
- [ ] 若器件支持低功耗、待机或掉电恢复，resume 后的重配、重读和再发布策略仍清楚。

### 8. 常见失效模式抽象

以下内容不是针对某一颗具体芯片。  
它们来自实际联调问题中的通用失效模式。

#### 8.1 构建不完整

- 现象：代码逻辑看似已接入，但目标文件、头文件路径或宏配置未进入构建系统，最终表现为功能缺失、链接缺符号，或行为与源码不一致。
- 约束：新增模块时，必须同步检查构建系统中的 `target_sources`、`target_include_directories`、宏定义与条件编译项。

#### 8.2 初始化失败后阻塞主循环

- 现象：某个外设初始化失败后直接 `while(1)`，导致系统失去诊断输出与后续恢复机会。
- 约束：初始化失败应优先返回错误，并交由上层实施限频重试、状态上报或降级运行，而不是永久阻塞。

#### 8.3 初始化顺序残缺

- 现象：只做了设备 ID 检查或只做了寄存器配置，没有执行 boot wait、软件复位、复位完成轮询等完整上电序列，导致器件偶现不启动、配置不生效或首包数据异常。
- 约束：初始化流程必须至少覆盖上电等待、ID 校验、复位恢复、关键配置与必要回读。不能把 ST 标准示例中的上电顺序裁掉一半。

#### 8.4 寄存器语义只剩结论，没有方法

- 现象：规范里只保留了要解耦、要可移植、要可靠这些结论，但缺少最关键的寄存器建模方法，导致后续实现容易回退到裸写寄存器、魔数散落或 App 层拼寄存器。
- 约束：规范除了给出分层结论，还必须保留 `ctx` 注入、读改写、多寄存器字段统一封装、位域使用边界这类可直接落地的实现方法。

#### 8.5 代码生成后用户逻辑丢失

- 现象：CubeMX 或类似工具重新生成后，自定义 include、变量、函数声明或调用入口被覆盖，表现为编辑器大面积报错、链接失败或运行逻辑丢失。
- 约束：所有用户扩展必须固定落在 USER CODE 或独立文件。每次生成后必须做一次最小回归检查，确认入口仍然存在。

#### 8.6 校准读取失败被伪装成合法默认值

- 现象：读取校准系数、OTP 或补偿参数失败后，驱动把结果默默置为 `0` 或默认值，初始化表面成功，但后续物理量计算持续错误。
- 约束：校准流程一旦失败，必须立即返回通信错误或配置错误。禁止把未读到伪装成刚好读到 0。

#### 8.7 ctx 注入存在，但平台仍硬编码资源

- 现象：接口设计上保留了 `ctx.handle` 或 `ctx.priv_data`，实际实现却直接绑定 `hspi1`、固定 GPIO 或固定外设实例，导致多实例、多器件或迁移时失效。
- 约束：若采用 ctx 注入，就必须让 Platform 实现真实依赖 ctx 传入的平台对象。否则宁可删掉无效字段，也不要制造伪注入接口。

#### 8.8 复位后首包尖峰直接外发

- 现象：系统复位或传感器重初始化后，最初几帧出现明显跳变，上位机误判为真实物理变化。
- 约束：对于连续物理量传感器，在 App 层增加预热收敛加稳定发布门控策略。内部可持续滤波和状态更新，但在连续稳定样本达到阈值前不对外发布。
- 诊断要点：调试回传必须带 `tick` 或序号，先定位是否存在复位点，再区分复位瞬态与真实环境突变。

#### 8.9 多字节原始数据解析被直接强转

- 现象：开发者把 `uint8_t buf[]` 直接强转成 `uint16_t*`、`int16_t*` 或 `int32_t*` 使用，导致字节序错误、未对齐访问风险或 24 位补码符号扩展错误。
- 约束：所有多字节寄存器值必须通过移位、掩码和显式符号扩展完成拼装，不能依赖编译器、平台字节序或未定义的内存对齐行为。
- 诊断要点：重点检查 16 位以上原始量的拼装函数，确认是否存在指针强转、联合体偷读或未处理高位符号位的情况。

### 9. 如何更新这份规范

后续更新按下面几条处理。

1. 只吸收多器件、多次联调里重复出现的共性问题，不追单个项目的临时细节。
2. 项目级规则回写 `docs/嵌软开发规范.md`。本文件只保留器件接入和实现细则。
3. 先修正文档歧义，再新增条目。新增规则最好同时落到正文和对应清单或失效模式里。
4. 目录、入口或自动加载关系变化后，顺手检查 `.github/copilot-instructions.md` 是否仍与本文件定位一致。
5. 版本段只保留关键里程碑，不展开成长流水。
