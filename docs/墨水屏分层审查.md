# Embedded Evidence Review

## Findings

核心分层成立：device 仅使用标准 C 与 IO 回调，platform 承担 SPI/GPIO/时基，GUI 与字模不操作硬件。以下按移入主要工程的影响排序；当前测试工程显示正常，不代表这些产品接入条件已经完成。详细调用与迁移清单见 [原厂墨水屏源码调用流程](原厂墨水屏源码调用流程.md)。本轮只更新文档，没有实施源码整改。

### [HIGH] 测试时钟入口永久占用执行流，错误返回后主程序没有恢复处理

- Location: `elinkTest/app/epd_bringup.c:237`, `elinkTest/app/epd_bringup.c:279`, `elinkTest/Core/Src/main.c:98`
- Trigger: 将现有 main 调用原样放入主要工程初始化阶段，期望其后启动其他业务；或 RTC/屏幕访问失败。
- Effect: 正常时 `epd_bringup_run_clock()` 不返回，后续初始化/主循环不能执行；失败时 main 丢弃返回码并进入空循环，无产品重试、上报或降级。
- Provenance: pre-existing
- Why it matters: 符合专用测试程序用途，但与 IC 规范要求的初始化失败有限返回并由上层处理不符，不能作为产品初始化入口复用。不是 device 的 BUSY 无超时问题，device 已有超时。
- Fix direction: 主工程拥有初始化、周期更新和恢复流程，复用 device/view；或由专属显示任务执行并处理错误。产品中不得忽略返回码；保留单一显示执行者，不制造第二个永久时钟循环。
- Verification: 在主要工程分别验证正常启动和 RTC/SPI/BUSY 失败，其他业务仍能执行，显示错误可观测且恢复次数有限；回归秒局刷、分钟快刷与 120 次清残影。

### [MEDIUM] 平台构造器固定 SPI2 与本板引脚，ctx 尚不能配置多个绑定

- Location: `elinkTest/platform/stm32_gdey029t94.c:43`, `elinkTest/platform/stm32_gdey029t94.c:58`, `elinkTest/platform/stm32_gdey029t94.c:94`, `elinkTest/platform/stm32_gdey029t94.h:14`
- Trigger: 主要工程使用其他 SPI/引脚，或调用者事先给 context 设置 SPI 句柄后期望构造器保留它。
- Effect: `make_io()` 覆盖为 `hspi2`；BUSY/CS/D_C/RES 忽略 context 使用全局板级宏，可能操作错误总线或引脚。
- Provenance: pre-existing
- Why it matters: SPI 回调实际消费 context，不应称为驱动没有注入；但构造器和 GPIO 仍是单板固定适配，不满足 IC 规范中的可配置资源注入要求。设备层 HAL 隔离仍成立。
- Fix direction: 单板迁移先替换 platform 的明确绑定；需多实例时将 SPI 与引脚放入真实上下文并由全部相关回调消费。GPIO 引脚与 MCU 类型继续留在 platform，不传入 device 寄存器逻辑。
- Verification: 在主要工程核对目标 SPI、GPIO 和 BUSY 极性；多实例配置时验证两份上下文互不覆盖、回调访问各自资源。

### [MEDIUM] 全局 Paint 与静态应用对象只有单调用者约束，没有并发保护

- Location: `elinkTest/gui/GUI_Paint.c:7`, `elinkTest/gui/GUI_Paint.c:26`, `elinkTest/app/epd_bringup.c:23`, `elinkTest/device/epd_gdey029t94.c:93`
- Trigger: 主要工程由多个任务/页面交错调用 GUI，或在刷新期间并发 init/sleep/刷新；共享 SPI 的其他调用者在 CS 操作与发送之间进入。
- Effect: `Paint_NewImage()` 覆盖同一个画布指针与方向状态，绘制可能进入错误缓冲；控制器命令、模式及 RAM 基准可能交错。仅锁住 HAL 发送不能保护此前的 D/C、CS 操作。
- Provenance: introduced
- Why it matters: 当前顺序演示和单线程时钟没有发现此并发故障；图形 API 已注释单调用者。进入多业务工程时必须落实所有权，不能因 device 使用 ctx 就认定 GUI 或控制器事务可重入。
- Fix direction: 一个显示执行者拥有画布、帧缓冲和 device，完整绘制序列及设备操作串行；共享总线由 platform/总线管理器在适当事务范围保护并配置。确有多画布并发需求后再将 GUI 改为实例上下文。
- Verification: 主要工程交错请求页面与休眠时不交错执行；共享 SPI 时检查 CS、D/C、传输和配置连续性。确认 IO 同步消费数据，不能把栈上命令直接交给立即返回的 DMA 实现。

### [MEDIUM] 演示应用直接使用设备内部 IO 与背景缓存，封装边界不完整

- Location: `elinkTest/app/epd_vendor_demo.c:85`, `elinkTest/app/epd_vendor_demo.c:131`, `elinkTest/app/epd_vendor_demo.c:133`
- Trigger: 将演示作为可复用模块移植，或后续修改设备对象的背景存储/上下文布局。
- Effect: 应用通过 `device->io` 调度演示等待，通过内部 `background_image` 发起清残影；演示与驱动结构布局、维护方式耦合。
- Provenance: introduced
- Why it matters: 没有在 app 拼寄存器，但“app 只使用设备语义 API”的封装尚未完全实现；设备层内部缓冲变化会迫使演示一起修改。公开 struct 是静态分配手段，不等于鼓励应用使用所有内部字段。
- Fix direction: 产品默认不带原厂演示；独立演示使用已传入 IO/应用延时，应用维护当前合成图或后续提供明确清残影语义接口。计数查询继续使用现有 getter，不直接改驱动标志。
- Verification: 演示不再读取 device 内部 IO/背景字段后重跑五窗、全屏局刷及两次演示清残影；原有数据顺序、图像和激活次数不变。

### [MEDIUM] 测试默认 FULL 且入口头依赖演示，直接复制会进入产品启动流程

- Location: `elinkTest/app/epd_vendor_demo.h:11`, `elinkTest/app/epd_bringup.h:5`, `elinkTest/app/epd_bringup.c:252`
- Trigger: 将测试入口复制到主要工程却未对所有相关编译单元显式设置 OFF，或只复制 bringup 而遗漏 demo 头文件。
- Effect: 每次复位先运行全部演示和清屏，出现多次全刷及延迟，随后才进入产品页面；漏头文件导致编译失败。OFF 仍不能消除 bringup 头的 include 依赖。
- Provenance: introduced
- Why it matters: FULL 是本测试工程按用户要求锁定的行为，当前配置正确；正式工程要求测试路径默认关闭且不形成隐式依赖，两者应由不同构建配置表达。
- Fix direction: 主要工程统一定义 `EPD_VENDOR_DEMO_MODE=0` 和三个诊断开关为 0；新的产品入口直接依赖 device/view，原厂演示保留在单独测试目标，不改变当前测试工程默认 FULL。
- Verification: 检查主要工程全部编译单元宏、启动日志与最终 MAP；上电直接进入产品页面，demo 资源及 9,472 B 工作区是否裁剪以主要工程链接结果为准。

### [LOW] 新 profile 与灰阶路径仍裸写命令，未统一复用现有命令常量

- Location: `elinkTest/device/epd_gdey029t94.c:504`, `elinkTest/device/epd_gdey029t94.c:539`, `elinkTest/device/epd_gdey029t94.c:636`, `elinkTest/device/epd_gdey029t94.c:674`
- Trigger: 后续维护初始化表、灰阶平面或更新控制值。
- Effect: 与文件顶部已有 `EPD_CMD_*` 重复表达同一命令，review 更难区分命令地址、参数和波形控制值。
- Provenance: introduced
- Why it matters: 命令仍正确位于 device，已有命令测试覆盖；这是规范中“魔数集中建模”的维护问题，不是当前显示故障。
- Fix direction: 复用已有命令宏，为专用 profile 参数与更新值命名；维持原厂数据和命令顺序。保留原厂 GUI 大小写命名属于兼容折中，若主工程统一 snake_case 应同步调用、include 和构建列表。
- Verification: 后续整理只改变常量表达后，Fake IO 捕获的四种初始化、RAM 平面和更新序列必须逐字节相同。

## Validation boundary

- Performed: 只读审查当前源实现与构建接入；比较 HEAD 区分既有/新增问题；检查未跟踪源文件清单；本轮资源可重复导入核对、16 项源码哈希、归档 HEX/BIN/Flash 读回哈希；目标源码/工程 diff 空白检查；更新两份文档并运行报告格式校验。
- Not performed: 未改固件源码/外设配置，未构建、下载、复位、读实时调试器、做硬件故障注入或电流/时序测量；未执行主要工程接入；未把归档主机测试当作本轮新测试；collector 整体不完整已列明。

120 次清残影是当前 device 公开的自动维护策略，并非隐藏于 platform 的业务逻辑，但快/局刷调用可能同时触发全刷；主要工程必须接受这一耗时/观感行为，或另行设计实例策略。当前同步 IO 契约、回调对象生命周期、profile 状态与缓冲要求见调用流程第 8.4/8.5 节。没有 power 回调、DMA、异步队列或 RTOS 的完成证据；原厂有限中文字体也不是完整 GB2312 字库。
